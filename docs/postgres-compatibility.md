# PostgreSQL event and error compatibility repair

GitHub CI run `37988813054` executed the real disposable PostgreSQL suites and reported three failures: assistant edit proposal persistence, concurrent corrected-report publication, and the expected HTTP 403 after revoked support consent. Thirty other SQL cases passed. This failed run remains qualification evidence; it must not be described as a passing review release.

The original foundation `event_type` CHECK allowed the initial v1 vocabulary but omitted `assistant.edit-proposed` and `coaching.corrected`. Writers now emit those valid application events, which the database could not accept. Migration `202610090007_event_contract.sql` extends that strict CHECK to exactly the currently supported application v1 types, including `interview.interaction`. It retains all original types and the `schema_version = 1` restriction. Unknown types and future versions remain rejected. Existing events are neither updated nor rewritten.

Apply this ordered additive migration through the controlled deployment process **before** deploying the corresponding web/worker writers. It depends on the foundation event table and can be applied without optional feature tables. Disposable test fixtures explicitly apply it; the operations qualification automatically applies sorted migrations. The application does not apply DDL at startup. Roll back only to readers that understand all types already persisted; an older strict reader correctly fails closed on an unknown event.

The adapter also previously preserved only `DomainError` after transaction rollback. A legitimate `HttpError` from the permissioned review callback was therefore incorrectly replaced with storage-unavailable HTTP 503. The repair preserves actual `HttpError` instances alongside `DomainError`. Plain objects, SQL driver errors, connection errors, and unknown exceptions remain converted to the static safe storage failure; SQL, credentials, learner content, and driver details are not returned.

Five deterministic transport tests cover rollback and trusted error preservation, rejection of status-shaped impostors, and redaction of connection/SQL errors. A contract-parity test prevents the strict SQL vocabulary from silently diverging from the typed application schema. A new real-SQL case verifies unknown event/version rejection, while existing assistant-edit and correction-publication cases cover the supported new event types.

No local Docker call was made for this repair. SQL behavior and the original three failures require a fresh GitHub CI execution after the fix is pushed. Static vocabulary parity and fake-transport tests do not establish that the migration or PostgreSQL workflows pass. Loader batching and UTC budget-window accounting are separate changes and are not part of this compatibility repair.
