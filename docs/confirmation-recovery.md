# Confirmation failure and retry behavior

Account data deletion, individual attempt deletion, finish coding, final submission, and pending AI edit acceptance/rejection keep their failure message inside the still-open confirmation dialog. During an outstanding mutation, Escape, the close icon, and the ordinary cancel action cannot dismiss that dialog. Once the operation settles, ordinary dismissal works again. A failed request does not clear the confirmation text or replace the learner's files. Successful operations close the dialog only after their expected acknowledgement is received.

## Explicit deletion recovery

Before sending DELETE, the client verifies the current signed-in owner without creating a replacement local identity. Each request carries that intended owner in `X-Practice-Owner`; both destructive HTTP routes reject a provided header that differs from the authenticated actor with HTTP 409 `owner_changed`, before service mutation. Legacy clients without the optional header retain ordinary authenticated ownership checks. It saves a bounded retry record in this tab's `sessionStorage`, under that owner and either the exact attempt ID or the account-data deletion scope. The record contains the original JSON request body and request ID, its first-intent time, and, for an attempt, a short display title. For an account-data deletion it also holds at most 50 unique session IDs captured from authenticated owned History before the first DELETE. That History read carries the same intended-owner header and rejects an account mismatch before returning IDs. These cleanup IDs remain metadata outside the unchanged wire body. It contains no source files, conversations, credentials, or provider secrets. Browser records are untrusted retry candidates: server authorization and request validation remain authoritative.

A network failure, 503, other non-success response, or incomplete success acknowledgement leaves that exact body recoverable. Closing and reopening the dialog or refreshing the same tab does not generate another deletion key. No deletion is sent automatically on load or when opening a dialog. The learner must explicitly confirm again; account-data deletion also requires retyping DELETE. If a deleted attempt disappears from the refreshed list after a lost response, History separately lists its pending deletion confirmation so the original result can still be recovered.

Both deletion APIs must return `deleted: true` before the UI marks deletion as acknowledged. Before removing any browser draft or pending action, the client rechecks the signed-in owner. If the identity changed or is unavailable, it retains browser data and saves an acknowledged marker with the original retry record. The dialog disables DELETE and offers **Clear acknowledged browser data**, which performs only local cleanup of the acknowledged owner’s pending scopes and captured draft IDs, never another deletion or sign-in. An explicit local cleanup remains available when the current identity is unknown or different. Other owners’ pending scopes and draft IDs remain. The acknowledged retry record survives same-tab refresh; an authenticated return to that owner can reopen it. Legacy draft keys lack owner metadata, so account cleanup removes only the IDs captured before the DELETE, never all draft keys. Older retry records without captured IDs cannot clear uncaptured drafts automatically. A failed browser-storage write or cleanup is reported; browser data clearance cannot be guaranteed when storage is unavailable. Only the exact HTTP 410 `request_deleted` error code is treated as a deleted-request marker. That marker clears only the corresponding deletion retry and leaves the error visible; starting a new action requires closing the dialog and explicitly opening a new confirmation. Other 410 errors remain uncertain and retain their original key.

The existing browser recovery policy refuses to send stored records that are at least 30 days old or have an invalid/future first-intent clock. The dialog offers **Discard expired deletion retry**, which clears only that intent and sends no DELETE. Starting a new action still requires opening a new confirmation and confirming it. This is conservative client behavior within the server's documented minimum replay guarantee; it is not permission to assume an old deletion never happened.

Session storage normally survives refreshes in one tab. It does not guarantee recovery after the tab is closed, browser data is cleared, storage is unavailable, or the learner signs out. Sign-out clears Lab recovery data; successful scoped account-data cleanup clears that owner’s Lab retry records and captured drafts, preserving other owners’ records and unrelated browser keys. A signed-out or changed account cannot dispatch a retry associated with the previously verified owner. Local development account deletion clears its identity cookie. The acknowledged response therefore leaves automatic browser cleanup pending, but the learner can explicitly complete the bounded local cleanup in the open dialog without restoring that cookie. If the page is refreshed after losing the local identity, the original authenticated deletion scope cannot be reopened through normal account controls; private browser data is retained instead of being swept. This development identity is not a hosted account-recovery mechanism.

## Existing workspace mutation guarantees

Finish/submit and edit decisions continue to use the existing owner/session-scoped pending mutation mechanism. An interrupted retry reuses the original semantic input, request ID, and wire revision even if polling observes a newer session revision. Changing semantic input selects a distinct intent. Definitive initial 4xx rejections follow the existing removal policy, while previously uncertain intents retain their identity. No new retry policy or endpoint was added for these actions.

Manual file changes save before a new finish or edit-decision mutation. If that save conflicts or fails, the requested action is not sent, the modal shows the failure, and the local draft remains available. Existing accepted-edit undo and support-review confirmation behavior is preserved. The intended-owner HTTP binding adds a guard while preserving existing server ownership permissions. Server freezing, immutable evidence, billing, job cancellation, and code execution are unchanged.

## Verification and limits

`tests/e2e/confirmation-recovery.spec.ts` uses explicit HTTP fixtures for delayed responses, 4xx and 503 failures, network acknowledgement loss, missing success acknowledgements, account changes before dispatch and during outstanding requests, unknown post-ack identity, owner-only cleanup, expired deletion recovery, trusted/unrelated 410 codes, manual-save conflicts, and identical retry bodies. It checks Escape and close-icon behavior while busy, normal dismissal afterward, draft retention, and deletion recovery across refresh even when History no longer contains the attempt. A mobile screenshot checks the account-deletion failure presentation.

These browser fixtures qualify UI/transport behavior only. They do not substitute for backend authorization/idempotency tests, a production persistence check, real provider or runner qualification, or an accessibility audit with assistive technology. `tests/deletion-owner-api.test.ts` checks the actual HTTP handlers against an in-memory service: owner mismatch before mutation, matching and legacy behavior, ordinary ownership checks, and exact replay. The existing local account-deletion smoke completes the ordinary explicit local cleanup without restoring its cookie, then restores its saved test cookie only for backend verification that the original private content is gone. No live model, speech, payment, or Docker call is required by these checks.
