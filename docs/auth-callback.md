# Sign-in link failure recovery

Checked 2026-10-09. This patch covers the email sign-in callback and its Settings recovery state. It makes no change to local identity, account ownership, deletion recovery, or billing.

`GET /auth/callback` exchanges a supplied code through the existing server-side Supabase client. A successful exchange retains the fixed `/interview-practice` destination. Missing codes, returned exchange errors, thrown exchange/client/cookie errors, and unusable application-origin configuration redirect to `/settings?error=sign-in-failed`. Provider and configuration text, callback codes, and query-supplied destinations are never reflected in the response. Redirects use status 303, `Cache-Control: no-store`, and `Referrer-Policy: no-referrer`. A callback-only header rule follows the global rule in `next.config.ts`; browser verification caught that the global rule otherwise overrode the route's header. Other paths retain their existing security headers.

The configured HTTP(S) application origin remains authoritative. If it cannot be resolved, only the relative fixed failure path is returned; the request Host, forwarded headers, and `next` parameter are not fallback redirect authorities. This callback has no user-selected `next` destination. Cookie reads and writes remain delegated to the existing Supabase `next/headers` adapter. A failed exchange does not explicitly clear an already signed-in account.

Settings recognizes only the exact `sign-in-failed` marker. Its accessible notice explains that the link may have expired, already been used, or encountered temporary unavailability; it does not claim to know the provider's reason. Signed-out hosted users can enter their email and explicitly send a new link. No request is made on landing, and the form disables while sending. A failed send retains the entered email and failed-link guidance, uses a generic error, and permits another explicit attempt. An acknowledged send clears the recognized failure marker from the current URL so refresh does not restore stale advice. Sending a link is not a claim that email was delivered or sign-in completed. A lost send acknowledgement may require another explicit email request; email-send idempotency is not introduced by this patch.

An existing signed-in user is asked to review that account and is not signed out automatically. Local mode continues to offer its explicit development identity action, while unconfigured accounts explain their unavailability without showing a nonfunctional email form. Unknown error query values and provider descriptions are not rendered.

## Verification and limits

`tests/auth-callback.test.ts` uses synthetic Supabase/client/cookie adapters to cover missing codes, returned and thrown errors, missing configuration, malformed and unsupported origins, fixed redirect destinations, and preservation of the cookie adapter's reads/writes. `tests/e2e/auth-callback.spec.ts` intercepts provider-related HTTP and checks explicit keyboard retry, delayed acknowledgement, returned/non-JSON/network failures, email preservation, refresh after acknowledgement, mobile width, existing accounts, local mode, and unconfigured mode. One browser test requests the real missing-code callback; that branch makes no provider exchange.

These tests establish local callback and browser behavior, not live Supabase delivery, expired-link behavior at the provider, hosted cookie deployment, or authentication security qualification. Those require the configured deployment and a separately authorized provider check. A malformed `APP_URL` still requires an operator fix; the relative recovery redirect makes that failure understandable rather than repairing configuration.
