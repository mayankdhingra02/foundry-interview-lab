# Design acceptance audit

This is a requirement audit of [the canonical design](design.md), conducted on October 9, 2026. It records remaining engineering work separately from human review, account access and deployment evidence. An implemented adapter, synthetic fixture or passing unit test does not complete the design's acceptance gates. P2 expansion remains conditional on validating the core learning loop; it is not silently counted as delivered.

The first assembled implementation was reviewed at `d68e012`. That audit found software omissions despite the working core flow. Follow-up PRs now address runtime identity in frozen evidence, late microphone permission after cancellation, schema-capability readiness, controlled model recording, public-test viewing, faithful evaluation variants, independent role-review scoring, a disposable component canary, configured lesson navigation and learner-visible retention rules. Later focused PRs implement confirmation recovery, timing/written controls, learner checks, substantive level drafts/prerequisites, optional bounded measurement, private corpus/model-review tools, operational references and sign-in recovery. The original planning estimates and design thresholds remain unchanged.

## Evidence that still requires people or infrastructure

Final-image resolution checks cover the known dev advisory chain in both web and worker; the advisory itself remains unresolved for security-owner review, as described in [dependency-audit.md](dependency-audit.md).

The earlier GitHub account no-runner restriction is historical. Fresh runs through PR #67 passed all four jobs. The #58 checkpoint included real Docker, 63 PostgreSQL cases, images/startup, 124 browser checks and the unchanged disposable load/restore gate; later checkpoint evidence is recorded separately in delivery status. The PR #57 deployment provisioning failure from registry rate limiting is retained; #58 added bounded retries for the same immutable images and passed. Newer focused commits require their own exact-head results. No billing settings were changed, no repository visibility was changed and no shared local Docker repair was used. See the delivery log for commit-specific results and remaining deployment boundaries.

Two experienced reviewers must independently inspect a curated benchmark and adjudicate disagreements. A protected holdout must remain outside prompt development. Record actual model outputs and evaluate interviewer, assistant modes and coach separately. Synthetic review labels, model agreement and valid evidence IDs cannot substitute for human assessment.

Content approval, supported-browser/screen-reader review, public-host isolation review, provider invoice/data-handling checks and the 20–30-person learner pilot remain open. The pilot must distinguish technical failures from withdrawal, record assistance, and compare fresh-task performance at matched difficulty. Do not infer learning effectiveness, fairness or hiring outcomes from fixture scores.

The deployment owner must choose hosting/region, verified identity, database, separate execution boundary, budgets, commercial terms, retention schedules, monitoring/alerts and rollback responsibility. Measured load, canary, restore and deletion exercises qualify that deployment. Repository code and a small localhost workload do not establish monthly availability, production capacity or RPO/RTO.
