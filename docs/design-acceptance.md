# Design acceptance audit

This is a requirement audit of [the canonical design](design.md), conducted on October 9, 2026. It records remaining engineering work separately from human review, account access and deployment evidence. An implemented adapter, synthetic fixture or passing unit test does not complete the design's acceptance gates. P2 expansion remains conditional on validating the core learning loop; it is not silently counted as delivered.

The first assembled implementation was reviewed at `d68e012`. That audit found software omissions despite the working core flow. Follow-up PRs now address runtime identity in frozen evidence, late microphone permission after cancellation, schema-capability readiness, controlled model recording, public-test viewing, faithful evaluation variants, independent role-review scoring, a disposable component canary, configured lesson navigation and learner-visible retention rules. Later focused PRs implement confirmation recovery, timing/written controls, learner checks, substantive level drafts/prerequisites, optional bounded measurement, private corpus/model-review tools, operational references and sign-in recovery. PR #72 adds version-bound prerequisites to all five original packages without altering their canonical scenario digests. PR #73 implements private pinned approval import for fixed synthetic staff examples, and PR #74 binds admitted inference policy through execution, retries and accounting. The configured second-provider follow-up adds a default-disabled Anthropic adapter and provider-bound operator recording; no automatic model fallback is enabled or qualified. The original planning estimates and design thresholds remain unchanged.

## Evidence that still requires people or infrastructure

Final-image resolution checks cover the known dev advisory chain in both web and worker; the advisory itself remains unresolved for security-owner review, as described in [dependency-audit.md](dependency-audit.md).

The earlier GitHub account no-runner restriction is historical. Final main [run 38012523330](https://github.com/mayankdhingra02/foundry-interview-lab/actions/runs/38012523330), exact commit `3bff37b` through PRs #1–74, passed all four jobs: 880 default tests (94 opt-in skipped), 49 isolated runner/content/capture checks, 64 real PostgreSQL cases, 156 browser checks, both deployment images/startup and the unchanged disposable operations/canary gates. Save p95 was 700.233 ms against 1,000 ms; all nine recovery checks passed and restore took 790 ms. The component canary passed eight checks with zero model/provider spend. This checkpoint predates the new second-provider follow-up and does not qualify its live adapter or chosen deployment. The #58 checkpoint included real Docker, 63 PostgreSQL cases, images/startup, 124 browser checks and the unchanged disposable load/restore gate; later checkpoint evidence is recorded separately in delivery status. The PR #57 deployment provisioning failure from registry rate limiting is retained; #58 added bounded retries for the same immutable images and passed. Those private-repository runs needed no billing or visibility change. The owner subsequently requested public visibility, which GitHub confirmed after #69. No billing settings or shared local Docker configuration were changed. Newer focused commits require their own exact-head results. See [CI](ci.md#public-repository-and-actions-scope) and the delivery log for source-publication boundaries, commit-specific results and remaining deployment conditions.

The authored scenario references, protected check source and checked-in development fixtures are now publicly readable. Their omission from learner/API/model contexts remains enforced, but public source cannot establish confidentiality or a protected evaluation holdout. The benchmark owner must account for that exposure, keep actual acceptance/holdout attempts and judgments outside Git, and use independently reviewed fresh transfer material for learning claims. Repository publication does not approve content rights or educational quality.

Two experienced reviewers must independently inspect a curated benchmark and adjudicate disagreements. A protected holdout must remain outside prompt development. Record actual model outputs and evaluate interviewer, assistant modes and coach separately. Synthetic review labels, model agreement and valid evidence IDs cannot substitute for human assessment.

Preserve the design's separation of development task variants from acceptance and learning transfer. Private attempt data on a public development variant alone does not satisfy that separation, and case-overlap tooling does not enforce it. Reviewed non-development variants, custody and matched fresh-task evaluation remain acceptance work. The design permits a qualified independent evaluation/pilot process; it does not require confidential packages to be imported into the current product harness.

Content approval, supported-browser/screen-reader review, public-host isolation review, provider invoice/data-handling checks and the 20–30-person learner pilot remain open. Mayank will coordinate friends-and-family recruitment; no volunteers or qualified reviewers are confirmed by that choice. The [pilot coordination handoff](pilot-coordination.md) separates learner participation, expert review and release ownership. The pilot must distinguish technical failures from withdrawal, record assistance, and compare fresh-task performance at matched difficulty. Do not infer learning effectiveness, fairness or hiring outcomes from fixture scores.

The deployment owner must choose hosting/region, verified identity, database, separate execution boundary, budgets, commercial terms, retention schedules, monitoring/alerts and rollback responsibility. Measured load, canary, restore and deletion exercises qualify that deployment. Repository code and a small localhost workload do not establish monthly availability, production capacity or RPO/RTO.
