# Operational failure support references

Interview Lab HTTP errors handled by `lib/server/http.ts` receive a freshly generated opaque UUID when their response status is 500–599. The response includes it as `error.reference` and `X-Practice-Reference`, with the existing private, no-store policy. The original HTTP status, application error code and safe message are preserved. Unexpected errors retain the existing generic 503 response. Request validation, authentication denial, ownership denial, quota exhaustion, deleted-request markers and revision conflicts (4xx) receive no reference or diagnostic posting.

`lib/server/diagnostics.ts` writes one bounded JSON record to server stderr: `schemaVersion`, `event: request.failed`, `reference`, integer `status` and an application-owned static category. Only exact known codes select a category; everything else is `unexpected_failure`. No request object, path, query, body, actor/session/job identifier, source code, transcript, report text, error name/message/stack, credential or raw provider response is accepted by this module. Incoming reference/request-ID headers and properties on thrown errors cannot choose the reference. Concurrent failures receive separate references.

The Interview Lab `ApiError` client displays “Support reference: …” only for operational statuses and a strictly validated canonical UUID v4. It keeps the status and original detail object available to existing mutation/recovery logic. The JSON reference and response header must agree when both are valid. The header can supply the reference if an intermediary returned a non-JSON error body. This adds no automatic retry, support message, content permission, provider request or new evidence. Other client-specific error classes and errors returned directly without the shared HTTP handler are outside this patch.

The diagnostic sink is best effort. Synchronous throws and asynchronous rejections do not replace or delay the original response; a displayed reference can therefore have no retained record during a collector outage. The default sink uses stderr and does not persist a second application database. Hosting must configure private log access, a limited diagnostic retention period, collection/alert delivery and a named support responder before claiming operational readiness. A learner may share the reference voluntarily; possession neither authorizes content inspection nor identifies an account. Existing permissioned support consent and audit remain required.

This is request-failure lookup, not full session/command/job/provider/runner/report distributed tracing. A fresh physical failure can have a new reference when an operator or learner retries the same logical action. References never enter session events, request fingerprints, quota postings, frozen snapshots or reports, and cannot act as mutation idempotency keys or learner-state evidence. Correlating broader existing operational identifiers, hosted collection and alert qualification remain separate deployment work.

`tests/support-reference.test.ts` verifies fixed content-free records, forged-input rejection, concurrent uniqueness, collector failure isolation, unchanged statuses/revision details/private caching, malformed-reference rejection and unchanged client mutation/recovery request behavior. These are injected deterministic contracts, not proof of hosted diagnostic delivery or a real incident response exercise.
