# Capability changes and acknowledged retries

Run and coding-assistant requests keep the same owner, operation, payload and request-key fingerprint as before. A valid acknowledged retry returns its original mutation result during the supported replay window, even if the execution flag, reviewed runtime configuration, AI flag, provider credential or operational execution hold subsequently changes. The attached capabilities describe current availability; the cached job acknowledgement does not promise that a queued job will execute after a hold or configuration change.

The HTTP adapter reads capability and execution-admission state before entering the practice-store transaction. A failed operational read captures a closed decision. It passes a synchronous, side-effect-free `FreshWorkGuard` to `SessionService.requestRun` or `requestAssistant`. The service invokes that guard only in the new-mutation callback, after its existing replay, changed-fingerprint, erased-request and ownership checks. The callback contains no operational database read or provider request. The worker independently checks current configuration and execution admission before doing external work.

Fresh work remains unavailable when its captured admission decision is closed. It creates no job, reservation, event, message, snapshot or request-cache entry. An altered payload under an acknowledged key remains 409; an erased original remains 410; a foreign or missing attempt remains 404. Existing mutation-rate admission still applies to genuinely new work. Authentication, origin checks and input validation remain required for retries, and expired or deleted content is never recreated to satisfy a replay.

`tests/replay-capabilities.test.ts` exercises the HTTP boundary with real in-memory transactions and mocked operational reads: exact retries after capability removal and shared holds, failed operational reads outside transactions, fresh rejection without mutation or debit, changed-payload/operation conflicts, cross-owner isolation and erased-request precedence. These deterministic checks make no model, Docker or hosted-service calls and do not establish live-provider qualification.
