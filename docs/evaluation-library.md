# Internal synthetic evaluation library

The **Evaluation** tab in `/internal` is a read-only view of the repository's curated developer-authored regression recipes. It supports inspection of scenario/condition provenance, recorded execution summaries, annotation status and label disagreements. Optional [private approval records](evaluation-approval.md) authorize inspection of validated candidate reports/proposals for exact human-approved synthetic examples. It is not an evaluation run, annotation editor or acceptance holdout; no actual approvals are supplied.

## Current evidence

The current repository contains 21 synthetic recipes, matching captured isolated execution facts for the ten original starter/reference snapshots, a blank human-review template, and no recorded model candidate set. Four custom snapshots add a partial repair, an intended alternative implementation and two declared interruption states; none has recorded execution. The alternative's validity and the interruption recovery behavior have not been qualified. Every displayed example therefore says **Human review pending**, its disagreement count is unknown, and example approval remains pending. A missing disagreement count is represented as `null`; it never becomes zero. The source file's developer curation is not human expert approval.

The existing `HumanAnnotations` format records independent-review attestations and adjudication, but contains no example-approval field. Even complete annotations cannot manufacture an approval decision. A separate strict display-approval bundle now records that decision with exact source/candidate/review binding, current authorized reviewer identities, validity and revocation. Human content/privacy review and actual decisions remain external requirements. Display approval is separate from model-quality qualification.

## Source and privacy boundaries

`lib/server/evaluation-library.ts` statically imports four fixed repository assets: `attempts.json`, `runtime-observations.json`, `human-review.template.json` and `baseline-summary.json`. An explicit server allowlist identifies the 21 curated recipe IDs. Unknown/duplicated recipes, mismatched benchmark identities and stale captured scenario/snapshot/suite digests fail validation. Custom file payloads also require a pinned scenario version, versioned snapshot, matching content digest and explicit execution state. New fixture families require a reviewed allowlist/source change. The library does not call a model, rerun code, read `PracticeStore`, initialize billing, inspect support records, accept an upload, or resolve caller-provided paths.

The API projects only published task briefs and rubric anchors, developer-authored synthetic dialogue/review focus, scenario/version/condition, captured run status and aggregate suite counts, immutable snapshot/fixture/context/runtime digests, and annotation/artifact metadata. The old-snapshot and unexecuted conditions remain explicit. Declared interruptions show no executed test evidence and do not appear as zero captured suites or genuine timeout/failure observations. The safe metadata identifies the snapshot version without exposing its custom files. Synthetic dialogue, including prompt injection, is displayed as quoted text and never interpreted as instructions or HTML.

Code files, reference solutions, test sources/titles, raw runtime output, execution commands, provider response IDs, reviewer IDs, human notes, private support records and saved learner data are excluded from these application responses. Unapproved model response text is excluded. An exact display-approved synthetic example may include bounded validated report/proposal text and evidence identifiers/digests; expiry, revocation or invalid binding removes that content. Disagreements expose anchored levels or boolean audit labels. Within the application, protected author material requires the existing purposeful **Scenario author preview** action; Evaluation GETs do not grant that access. The same checked-in author assets and synthetic development recipes are publicly readable in Git following the owner's visibility change. This endpoint boundary does not establish source confidentiality. Actual learner, acceptance and holdout artifacts remain outside this allowlist and outside Git; see [public-source scope](ci.md#public-repository-and-actions-scope).

`GET /api/internal/evaluations` returns list metadata and qualification prerequisites. `GET /api/internal/evaluations/<known-id>` returns the projected example. Both require the server-verified actor and the existing exact `ADMIN_USER_IDS` staff policy on every request. Local identities remain forbidden in production. Responses use `Cache-Control: private, no-store`. Query parameters that attempt to select a different source are rejected. Writes and arbitrary actions are rejected. The evaluation branch dispatches before initializing the review/practice service, so storage or payment configuration is not needed to inspect repository fixtures. The surrounding staff console retains its separate support-tool behavior.

## Reviewed artifacts and disagreement interpretation

`buildEvaluationRepository` accepts the existing `CandidateSet` and `HumanAnnotations` formats as an internal code interface, not an HTTP upload interface. It reuses the benchmark's schema, evidence/context binding, guarded output validation, complete criterion coverage, distinct reviewer checks and adjudication chronology. Matching candidate digests are required before any review labels are attributed. Edited outputs, stale contexts or mismatched candidate digests do not inherit old labels.

Two bound distinct reviewer records permit a label-difference display; missing labels remain missing. Complete valid adjudication records show the adjudicated levels/flags beside each disagreement. An incomplete pair or adjudication remains pending/partial. Reviewer identity and independence attestations still need the actual human review process. Imported metadata cannot independently establish that a provider generated a response.

Without explicit private review configuration, the loader passes no candidate set and the blank annotation template. To expose future synthetic reviewed artifacts, complete the existing offline review workflow in [evaluation.md](evaluation.md), verify their synthetic provenance and absence of private material, and provision the exact pinned external bundle described in [recorded approval](evaluation-approval.md). Runtime configuration selects only that private review bundle; recipes/captures remain fixed. Learner exports, support cases, private acceptance corpora and HTTP uploads remain forbidden. No annotation or approval decision is generated by this feature.

Qualification uses the existing release-gate calculator and clearly identifies the stored deterministic baseline timestamp. Opening the screen does not rerun those regressions or qualify a model. The 40-attempt minimum, recorded provider candidates, independent expert adjudication, operational/security/accessibility review and learner pilot remain separate release obligations.

## Verification

`tests/evaluation-library.test.ts` checks current pending status, sparse/injection/unexecuted/stale conditions, protected-material projection, matching hypothetical artifact formats, disagreement mechanics, missing/duplicate reviewers, changed candidate/context rejection and source validation. `tests/evaluation-variants.test.ts` additionally checks custom snapshot integrity and bounds, explicit capture identity, interruption/no-execution context binding, absence of borrowed test facts, and custom-code stripping. Hypothetical unit records stay in test memory; they are never saved as human annotations or provider output.

`tests/evaluation-api.test.ts` checks anonymous/ordinary/near-match/local-production denial, exact allowlist revocation, private caching headers, fixed sources, read-only routes, and absence of practice-service initialization. `tests/e2e/evaluation.spec.ts` uses explicitly synthetic frontend contract fixtures for pending labels, escaped injection text, unknown disagreements, filter behavior, keyboard tabs, mobile overflow, access revocation and denied-fetch behavior. These fixtures establish interface behavior; they do not establish hosted authentication, real expert approval or live AI quality.
