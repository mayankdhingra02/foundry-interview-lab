# Scenario registry batching and transport measurement repair

Every trusted persistence transaction still verifies the immutable public scenario manifest for every represented scenario/version, including unchanged sessions and exact replays. Previously that meant one INSERT/one SELECT per saved session. Ten sessions sharing a package added 20 registry roundtrips to every save/replay while the global lock was held.

The adapter now deduplicates identical package/version manifests, rejects inconsistent same-version manifests within the proposed corpus, and performs one parameterized JSON-recordset insert plus one joined hash verification query. Registry traffic is two requests for any nonempty admitted package set. Missing, duplicate, unknown or mismatched verification rows cause rollback. No scenario/evidence checks, owner constraints, row/byte bounds, SQL snapshot, or advisory lock is omitted. No timing threshold is changed. PostgreSQL's [JSON recordset functions](https://www.postgresql.org/docs/16/functions-json.html) provide the typed SQL input; manifest JSON is a parameter, never executable SQL.

The count-only transport diagnostic also uses the unambiguous alias `transport_source`. The earlier alias `source` collided with the event table's relational `source` column: `to_jsonb(source)` measured a scalar rather than that whole row and the safe size check rejected it. [Run 37993840372](https://github.com/mayankdhingra02/foundry-interview-lab/actions/runs/37993840372) failed its new SQL diagnostic case; 42 other PostgreSQL cases passed. No load measurement was produced by that failed run. This repair preserves the failure and still requires the real SQL case to pass.

Seven synthetic transport tests cover constant registry query count, distinct packages, parameterization, mismatch/missing/duplicate/unknown rows and within-corpus version conflict. They do not execute PostgreSQL or establish latency. Existing SQL tests and the unchanged ten-session/50-save load, replay, fencing and restore gate run in fresh-host CI. Its save p95 must remain below 1000 ms. Earlier misses of 1,102–1,553 ms remain open evidence until the new code is measured; no favorable older run qualifies this revision. Projected/full JSON row-text bytes describe the same synthetic corpus and exclude protocol framing; they are not production throughput.

Real qualification: [run 37995389344](https://github.com/mayankdhingra02/foundry-interview-lab/actions/runs/37995389344) passed the repaired SQL diagnostic but missed p95 at 1,123 ms; all nine recovery checks passed. [Runtime run 37995581500](https://github.com/mayankdhingra02/foundry-interview-lab/actions/runs/37995581500) inherited this batching and passed all four jobs, 45 SQL cases and p95 818 ms. The same corpus measured 2,155,823 full-row versus 1,166,133 projected JSON bytes. Preserve both outcomes; neither establishes a hosted traffic envelope.
