# Final-image development dependency isolation

`scripts/operations/container-smoke.ts` applies the same package-resolution absence check to both already-built qualification images: the running web image and the worker image before its runtime imports. The checked packages are `eslint`, `eslint-config-next`, `@next/eslint-plugin-next`, `fast-glob`, `micromatch`, `braces`, `typescript` and `vitest`. This covers the identified development advisory chain and the existing lint/compiler/test-tool checks.

Any successful `require.resolve(package)` exits the image check with status 1. A resolver error other than `MODULE_NOT_FOUND` also fails the command. The success marker is emitted only after every package is unresolved. The web result retains `developmentToolsOmitted`; the worker adds `workerDevelopmentToolsOmitted` and separately requires the exact runtime-import success marker. A nonzero Docker/Node command rejects the smoke script; a false summary check sets its exit status to 1. Commands use `execFile` argument arrays: the generated JavaScript is one `node -e` argument, with no shell expansion or external package names.

The existing explicit `FOUNDRY_CONTAINER_SMOKE=1` gate, actual provisioned immutable `PYTHON_IMAGE_ID`, fixed local qualification image tags, `--pull=never`, read-only containers and restricted privileges remain in effect. The smoke check does not build or pull images, mount a Docker socket, run learner code, contact providers, or restart/prune Docker. It uses the existing cleanup for its named web container and `--rm` worker processes. Actual execution belongs on the dedicated fresh CI VM with the already-built images; source/type/lint verification does not qualify final-image contents.

This proves only that the named packages cannot be resolved from the application's runtime context in those tested image bytes. It is not a full filesystem inventory, SBOM, vendored-code analysis, OS/Docker-CLI scan or proof that every vulnerability is absent. Inaccessible nested copies or vendored implementations require separate inventory/inspection. Development and build still install the advisory-bearing graph. The dependency advisory remains unresolved; this isolation check neither patches it nor accepts the remaining risk. See the separate dependency advisory assessment for its source/lockfile evidence and remediation limits.
